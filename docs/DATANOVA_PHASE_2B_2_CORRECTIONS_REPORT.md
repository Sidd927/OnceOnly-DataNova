## 4. API Validation: Before vs After

### 4.1 Reversed Interval (`unit_start > unit_end`)

**Request:**
```http
POST /api/reconcile/compare HTTP/1.1
Content-Type: application/json

{
  "candidate": {"registry": "VCS", "batch_id": "18453", "unit_start": 200, "unit_end": 100, "claimant": "Alpha Corp"},
  "existing": {"registry": "VCS", "batch_id": "18453", "unit_start": 100, "unit_end": 200, "claimant": "Beta LLC"}
}
```

- **Before:** `HTTP 500 Internal Server Error` (Unhandled `ValueError: Invalid candidate interval: start (200) > end (100)`).
- **After:** `HTTP 422 Unprocessable Entity` with structured validation payload:
  ```json
  {
    "detail": [
      {
        "type": "value_error",
        "loc": ["body", "candidate"],
        "msg": "Value error, unit_start (200) cannot exceed unit_end (100)",
        "input": {
          "registry": "VCS",
          "batch_id": "18453",
          "unit_start": 200,
          "unit_end": 100,
          "claimant": "Alpha Corp"
        }
      }
    ]
  }
  ```

### 4.2 Negative Boundary (`unit_start < 0`)
- **Before:** Accepted into interval engine; negative unit numbers mathematically processed.
- **After:** `HTTP 422 Unprocessable Entity` (`msg: "Value error, unit_start must be non-negative, got -10"`).

### 4.3 Zero Boundary (`unit_start = 0`)
- **Behavior:** Valid serial index. `POST /api/reconcile/compare` with $[0, 50]$ vs $[51, 100]$ returns `HTTP 200` with `candidate_units: 51`, `overlap_type: "ADJACENT"`.

### 4.4 Single-Unit Interval ($s = e$)
- **Behavior:** Valid serial index. `POST /api/reconcile/compare` with $[500, 500]$ vs $[500, 500]$ returns `HTTP 200` with `candidate_units: 1`, `overlap_units: 1`, `overlap_type: "EXACT_OVERLAP"`.

## 7. Semantic Classification Review Findings

1. **Parent-Subsidiary Relationships:**
   - Overlaps between parent companies and subsidiaries (e.g. *Microsoft Corporation* vs *Microsoft Ireland Operations Ltd*, *TotalEnergies SE* vs *TotalEnergies Renewables USA LLC*) resolve strictly to `SAME_UNITS_RELATED_CLAIMANTS`.
   - The engine explicitly distinguishes this from `SAME_UNITS_SAME_CLAIMANT` (which requires identical canonical entities).
   - Downstream recommendation: *"Determine which entity (parent or subsidiary) holds primary carbon reporting rights."*
2. **Shared Intermediaries:**
   - When two claims share an intermediary broker (e.g. *Patch on behalf of Lenovo* vs *Patch on behalf of Dell*), the engine extracts the underlying beneficial principals (*Lenovo* vs *Dell*).
   - Comparing *Lenovo* and *Dell* yields `DIFFERENT_ENTITIES`.
   - The overlap resolves to `ALLOCATION_CONFLICT`, confirming that shared brokerage does not falsely imply common beneficial ownership.
3. **Multiple Intermediaries for Same Principal:**
   - When different brokers retire credits for the same principal (e.g. *Patch on behalf of Lenovo* vs *TBK Group on behalf of Lenovo*), the engine matches *Lenovo* as the common principal, resolving to `INTERMEDIARY_ATTRIBUTION`.

## 9. Remaining Limitations

1. **Internal Evaluation Benchmark:** The 36 reconciliation cases are curated synthetic and historical test vectors designed to evaluate boundary conditions and edge cases. They validate algorithmic correctness but do not establish real-world double-counting prevalence across voluntary carbon registries.
2. **Corporate Hierarchy Scope:** Corporate parent-subsidiary detection uses token-based name morphology and suffix parsing. For entities with completely disparate legal names (e.g., *Alphabet Inc.* and *Waymo LLC*), corporate hierarchy requires an external corporate registry index (e.g., LEI or OpenCorporates), which is marked for future roadmap exploration.
